2 Credential recovery and updates: cryptographically random 32-byte reset tokens with expiry. RETAIN We retain this feature. For self-service password recovery, our backend generates a cryptographically secure 32-byte random token using crypto.randomBytes(32). To protect our database, we only save the SHA-256 hash of the token in the users table with a strict 1-hour expiration. Once used, the token is reset to NULL so it cannot be reused, and our API returns a generic success message so an attacker cannot enumerate valid school emails. Planned Live Test:

This resolves our instructor's review flag regarding the unspecified algorithm. In our authService.js, passwords are never stored in plaintext; we hash them using the bcrypt library (^6.0.0) with salt cost factor 12 (BCRYPT_SALT_ROUNDS = 12). Password hashes are strictly excluded from all API responses and audit logs across all user roles. Planned Live Test:

SESSION SECURITY

A4
Instructor review flags (clarify before approval): “All routes” require sessions conflicts with the public student fault-report flow. Specify the public endpoints and their validation/abuse controls. Client auth-check.js does not replace server authorization. Polling/connection pools do not guarantee high uptime. QR token uniqueness is not proof of expiry or replay prevention. Do not add electronic locks: the stated device monitors physical keys. Source wording includes password hashes, but does not identify bcrypt despite a bcrypt-related reference.
Our Capstone Group Clarifications:
  1. Public endpoints vs. sessions: In our system, staff routes require sessions, while student fault reporting is intentionally public at kiosks (/verify-student-id, /student-cooldown, /submit, /pc-info) with IP rate limiting (5 / 10m), PC cooldown (1 / 1m), and MySQL student cooldown (30m).
  2. Client auth-check.js vs. server auth: auth-check.js is only a client-side anti-flash visual redirect. Our Express server independently validates active session roles on every API request via requireAuth and requireRole.
  3. Polling and connection pools: 3-second polling is an interface refresh mechanism, and connection pooling manages MySQL resources. Infrastructure 99.9% uptime is managed by Railway.
  4. QR expiry & replay prevention: Scanning student ID QR codes generates ephemeral HMAC SHA-256 tokens with 16-byte random nonces and 10-minute expiry; tokens are atomically marked Used_At = NOW() in MySQL upon submission, preventing replay.
  5. Physical keys (no electronic locks): LabSync is an IoT physical key monitoring dock using ADC resistor dividers on pins D32/D33. Unauthorized key removal sounds an onboard buzzer and logs an alert. No electronic locks or solenoids are added.
  6. Password hashing algorithm: Passwords are hashed using bcrypt (^6.0.0) with 12 salt rounds (BCRYPT_SALT_ROUNDS = 12) in authService.js. Stored hashes use standard $2b$12$... format.
