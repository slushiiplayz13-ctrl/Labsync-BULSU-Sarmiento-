Group Demonstration & Examination Testing Script for Live Deployed Application

Category A: Login and Account Security
#1 Account Provisioning, Session Checks & Public Kiosk Access RETAIN
Target URL: /api/schedules/save  |  /public/report.html
How to Test: 1. Open an Incognito/Private window.
2. Paste https://labsync-bulsu-sarmiento-production.up.railway.app/api/schedules/save directly into the address bar.
3. Next, open /public/report.html in the same incognito window.
Expected Result: Protected API returns HTTP 401 Unauthorized (access blocked). Meanwhile, the student fault-report page opens cleanly without requiring any login.
What to say: "Our server requires sessions on staff routes, but public student fault reporting is intentionally accessible so students at kiosks aren't blocked by login."
#2 Credential Recovery: 32-Byte Cryptographic Tokens & 1-Hour Expiry RETAIN
Target URL: /recover-password.html
How to Test: 1. Open /recover-password.html and enter a test email address.
2. Submit the form, then open the Railway MySQL database users table.
Expected Result: The screen displays a generic confirmation message (preventing email enumeration). In MySQL, Reset_Token stores only a 64-character SHA-256 hash, and Reset_Token_Expiry is set to exactly 1 hour. Once reset, it clears to NULL.
What to say: "We generate 32 random bytes, store only the SHA-256 hash in MySQL with a 1-hour expiration, and reset it to NULL upon single use."
#3 Secure Password Handling: bcrypt with 12 Salt Rounds RETAIN
Verification: Railway MySQL Console / phpMyAdmin / DBeaver
How to Test: 1. Open Railway MySQL Query tab and run: SELECT Email, Password FROM users LIMIT 3;
2. Inspect the password column string format.
Expected Result: Every password begins with $2b$12$.... This proves standard Modular Crypt Format using bcrypt at 12 salt rounds. Plaintext is never stored.
What to say: "We use bcrypt (^6.0.0) with BCRYPT_SALT_ROUNDS = 12. Plaintext passwords are never saved, and hashes are omitted from all API outputs."
Category B: Session Security
#4 Session Fixation Defense: ID Regeneration on Login & Logout Destroy RETAIN
Target URL: /login.html  |  DevTools Application > Cookies
How to Test: 1. Press F12 > Application > Cookies > note the connect.sid value.
2. Log in with your MIS or Faculty account.
3. Check connect.sid again. Then click Logout.
Expected Result: The connect.sid cookie value changes completely after login (preventing fixation). After logout, the cookie is deleted and destroyed on the server.
What to say: "Our auth controller runs req.session.regenerate() upon successful authentication and req.session.destroy() upon logout."
#5 Cookie Protection: HttpOnly, Secure & SameSite Flags RETAIN
Verification: Browser DevTools Console & Application tab
How to Test: 1. In DevTools Cookies tab, check the columns for connect.sid.
2. Switch to the Console tab and run: console.log(document.cookie);
Expected Result: DevTools shows HttpOnly = ✓, Secure = ✓, and SameSite = Lax. The console prints an empty string or omits connect.sid (XSS theft blocked).
What to say: "Our session cookies have HttpOnly and Secure flags enabled, meaning malicious JavaScript cannot steal user session tokens."
#6 Session Lifecycle: 10-Minute Rolling Inactivity Timeout & HSTS RETAIN
Verification: DevTools Network Headers & Idle State Test
How to Test: 1. In DevTools Network tab, inspect any response header for Strict-Transport-Security.
2. Log in to dashboard, remain inactive for >10 minutes, then click any action.
Expected Result: Response header contains Strict-Transport-Security: max-age=15552000. After 10 minutes of inactivity, API returns 401 SESSION_EXPIRED.
What to say: "We enforce 180-day HSTS for transport security and a 10-minute idle inactivity timeout in auth middleware to prevent unattended station takeovers."
Category C: Access Control
#7 Role-Based Access Control (RBAC): Faculty, IT Head, MIS & OJT RETAIN
Verification: Browser DevTools Console (as Faculty)
How to Test: 1. Log in with a Faculty account.
2. In DevTools Console, execute an administrative call:
fetch('/api/mis-staff', { method: 'POST', headers: {'Content-Type':'application/json'}, body: '{}' }).then(r => alert('Status: ' + r.status));
Expected Result: Alert shows Status: 403 Forbidden. The server checks the live database role on every request and blocks unauthorized privilege escalation.
What to say: "Our requireRole middleware queries live MySQL data on every single API request, rejecting unauthorized roles with HTTP 403."
#8 Privileged Actions vs. Public Reporting Separation RETAIN
Target URL: /public/report.html vs. /api/faculty
How to Test: 1. Submit a valid fault report on /public/report.html without logging in.
2. In the same unauthenticated browser, try calling: fetch('/api/faculty/add', { method: 'POST' }).then(r => alert('Status: ' + r.status));
Expected Result: Public fault report succeeds. Administrative call returns Status: 401 Unauthorized. Proves strict segregation between public and admin routes.
What to say: "We keep student kiosks public to eliminate reporting friction, while all administrative management routes strictly enforce sessions and roles."
