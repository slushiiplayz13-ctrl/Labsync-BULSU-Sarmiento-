### Instructor Review Flags (Clarifications Before Approval)

> **Instructor review flags:** “All routes” require sessions conflicts with the public student fault-report flow. Specify the public endpoints and their validation/abuse controls. Client auth-check.js does not replace server authorization. Polling/connection pools do not guarantee high uptime. QR token uniqueness is not proof of expiry or replay prevention. Do not add electronic locks: the stated device monitors physical keys. Source wording includes password hashes, but does not identify bcrypt despite a bcrypt-related reference.

#### 1. Public Student Fault Reporting vs. Session Requirements
- **Our Clarification:** In our system, only administrative, schedule management, and faculty account routes require authenticated sessions. We intentionally made public student PC fault reporting unauthenticated so that students at laboratory kiosks can report issues immediately without needing an account.
- **Our Public Endpoints:** `POST /api/reports/verify-student-id`, `GET /api/reports/student-cooldown`, `POST /api/reports/submit`, `GET /api/reports/pc-info`.
- **Our Abuse Protections:** IP rate limiting (5 reports / 10 min), per-PC duplicate cooldown (1 report / 1 min per IP+PC), and an authoritative 30-minute student number cooldown enforced in MySQL (`student_report_cooldowns`).

#### 2. Client-Side `auth-check.js` vs. Server Authorization
- **Our Clarification:** Our client-side `auth-check.js` is strictly an interface anti-flash check running in the browser `<head>` to prevent unauthorized page rendering before redirecting to `login.html`.
- **Our Server Authorization:** Every protected endpoint independently enforces `requireAuth` or `requireRole(...)` via Express middleware, querying MySQL live role data on each request. Even if a user disables JavaScript or makes direct API calls, our server rejects them with HTTP 401 or 403.

#### 3. Polling and Connection Pools vs. Availability Claims
- **Our Clarification:** We clarify that 3-second dashboard polling is an interface refresh mechanism (`setInterval` in `mis-keys.js` and `auth-check.js`), and connection pooling (`mysql2.createPool`) is for managing database resources. Neither guarantees 99.9% uptime. Uptime SLA is handled externally by our cloud host (Railway).

#### 4. QR Token Expiry and Replay Prevention
- **Our Clarification:** When a student scans their physical ID QR, our server generates an ephemeral capture token signed with HMAC SHA-256 containing a 16-byte random nonce, room/PC binding, and a 10-minute expiration (`studentVerificationService.js`). The session is recorded in `student_verification_sessions` and atomically marked as used (`Used_At = NOW()`) inside an ACID transaction upon submission, preventing any replay attacks.

#### 5. Physical Key Monitoring vs. Electronic Locks
- **Our Clarification:** We confirm that our LabSync hardware dock is strictly an **IoT physical key monitoring and docking device**, not an electronic door lock or solenoid-actuated lock. Key presence is monitored via analog ADC voltage divider resistors (`KEY_PIN_203` on D32, `KEY_PIN_204` on D33). Removing a key without scanning triggers a physical buzzer alarm and generates an `IOT_UNAUTHORIZED_KEY_REMOVAL` audit event.

#### 6. Password Hashing Algorithm Identification
- **Our Clarification:** We confirm that our system uses **bcrypt** (`^6.0.0`) with 12 salt rounds (`BCRYPT_SALT_ROUNDS = 12`) across all account provisioning, user profile updates, and password reset flows. The database stores standard modular crypt hashes (`$2b$12$...`).
